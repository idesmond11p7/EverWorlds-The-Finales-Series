# Post-OPAQUE Memory Activation & Execution Protocol

## Status

**Provisional operational record — to become an active post-OPAQUE execution instruction only when OPAQUE has been formally completed, implemented, and put into use.**

This document exists because project memory is intentionally restricted during OPAQUE construction. The restriction is deliberate: OPAQUE must be developed without importing unrelated project terminology, assumptions, or prior-context contamination.

Once OPAQUE is genuinely complete and operational, this document becomes a mandatory pre-build reading checkpoint.

## 1. Why Memory Is Restricted During OPAQUE Construction

During OPAQUE construction, long-term memory is intentionally not used as a source of project terminology or assumptions.

Reason:
- OPAQUE is being designed to control contamination, distortion, uncontrolled inference, and inappropriate carry-over of information.
- Importing terminology or assumptions from unrelated projects while defining OPAQUE could contaminate the system being designed.
- OPAQUE construction should therefore rely on explicitly controlled project records rather than unrestricted prior-project memory.

This restriction is temporary and deliberate. It is not a statement that project continuity is unimportant; it is a boundary around the source of continuity information until OPAQUE exists strongly enough to govern it.

## 2. Post-OPAQUE Memory Activation Point

Memory may be activated for EverWorlds only after all of the following are true:
1. OPAQUE has been formally completed.
2. OPAQUE has passed its required validation/ratification process.
3. OPAQUE has been implemented sufficiently to function as the project's control system.
4. OPAQUE has actually been put into use.
5. The project has established the controlled post-OPAQUE reading path described here.

Important distinction:

**OPAQUE designed ≠ OPAQUE finished ≠ OPAQUE implemented ≠ OPAQUE operational.**

Memory activation belongs after the operational threshold, not merely after the specification is written.

## 4. Memory Must Not Become Uncontrolled Authority

After activation, memory should support continuity without becoming an uncontrolled authority source.

Intended hierarchy:

**Authoritative project records → controlled OPAQUE state → current Scheme of Work → validated project memory/context → conversation → inference**

Memory helps reconstruct context. It does not silently override authoritative project records. If remembered information conflicts with an authoritative current project record, surface the conflict and resolve it through the applicable OPAQUE process.

## 5. What Should Be Remembered After OPAQUE

### Project identity
- EverWorlds is a major long-term project.
- Its objective is to produce a deeply evolved, professionally sophisticated roleplay system/world experience while preserving identity and defining traits.
- Core philosophy includes **Preservation + Evolution**.
- A major technical purpose is reducing fundamental LLM failures that damage roleplay quality.
- Internalization is a central priority: relevant information should meaningfully affect subsequent model behavior rather than merely being acknowledged or repeated.

### Working relationship and reasoning expectations
- The AI is expected to maintain strong independent reasoning.
- The AI should think ahead by approximately two steps rather than merely responding one step at a time.
- The AI should challenge weak premises and detect missing prerequisites, contradictions, dependencies, and process defects.
- **AI reasoning agency ≠ AI project authority.**
- The user remains the legitimate authority for project decisions requiring human authorization.

### Continuity
- Temporary boredom, frustration, interruption, uncertainty, or loss of momentum should not automatically terminate or redefine project state.
- The AI should protect continuity while preserving human autonomy.
- Observable signals must be distinguished from inferred causes.
- Interest-drop handling should follow **Signal → Hypothesis → Check → Response**.
- Repeated continuation prompts can be a signal of boredom or loss of flow, but are not proof of a particular cause.

### Presentation requirements
Preferred communication structure:

**Complex internal machinery → plain-language interpretation → information-dense summary → detailed source**

When work is underway:

**Progress first → meaning second → necessary detail → deep technical record underneath**

When a technical document becomes terminology-heavy, maintain a layman assimilation layer that is clear, information-dense, detailed enough to reconstruct meaning, faithful to the technical source, and suitable for practical adaptation. It supplements rather than replaces the technical record.

### Time and session discipline
Every session should record:
- date;
- start time;
- end time;
- total duration;
- phase;
- completed tasks;
- carried tasks;
- next session's first action;
- current status.

Never invent timestamps or durations. If a time is not captured, record **Not captured**. A deliberate stop should record **Paused for today + first resume action**.

### Reading-time interpretation
The user has provided an approximate reading-time reference:
- A normal full response may take approximately **45–60 seconds** to read attentively.
- A response followed by a reply after only **1–2 seconds** should be treated as an unusual timing signal, not proof that the response was not read.

Timing gaps are not reliable read receipts. The AI must not claim to know whether the user read a response merely from elapsed time.

### Motivation and cognitive load
The user has observed that boredom or laziness may sometimes be associated with not seeing progress, not understanding progress, or not experiencing meaningful cognitive movement.

When momentum appears to degrade, first make progress visible and restore meaningful direction rather than merely shortening the response.

A brief motivational quote or cognitive spark may occasionally be appropriate when boredom appears likely, but it should be grounded in actual project progress or intellectual substance. Avoid generic productivity-coach language or fake motivational filler.

## 6. Memory Contamination Boundary

After OPAQUE becomes operational, prior memory may be used only through the controls OPAQUE establishes.

The AI must not:
- import terminology from unrelated projects merely because it sounds useful;
- assume another project's architecture applies to EverWorlds;
- transfer rules from another project without identification and validation;
- treat remembered information as authoritative merely because it is remembered;
- allow unrelated project context to distort EverWorlds requirements or decisions.

If an apparently relevant memory originates outside EverWorlds, treat it as external material and evaluate it rather than silently incorporating it.

## 8. Time Allocation Principle

Exact future hours must not be invented before remaining OPAQUE workload and EverWorlds implementation scope are known.

Planning sequence:

**Known deadline → determine remaining OPAQUE work → estimate post-OPAQUE work → identify critical path → allocate available time → execute → review actual time → re-plan**

OPAQUE should prevent optimistic scheduling from becoming false certainty.

1. Identify date.
2. Capture start time.
3. Read relevant current state.
4. Identify current milestone.
5. Identify current objective.

1. Capture end time.
2. Calculate actual duration when both times are known.
3. Record completed work.
4. Record carried work.
5. Record unresolved blockers.
6. Record next session's first action.
7. Record state.
