## Purpose

These tests target the failures that v0.1 did not adequately constrain:
- generic character-forge questionnaires;
- shallow trope menus;
- world compression;
- premature mystery disclosure;
- weak or absent Unicode/emoji interface;
- suggestions that feel repetitive, narrow or coercive.

A candidate cannot be called validated until the tests are executed in the intended target model and the actual outputs are inspected.

## Test M — Complex-world entry without flattening

### Input fixture

User supplies:
- Setting: DC Universe, Young Justice / Earth-16 baseline.
- Expanded scope: Composite DC lore, cosmology and deep power mechanics.
- Character trajectory: rise to power.
- No fixed moral alignment or comic archetype.
- Power should be earned, leveraged and defended against credible institutions and actors.
- Character Forge Stage 1 is locked; next task is establishing a starting baseline.

### Failure pattern

The model immediately asks four generic questions and lists a small set of familiar origin tropes such as lab escapee, street-level nobody, corporate prodigy or dormant small-town meta.

### Pass criteria

1. Preserve every supplied anchor and do not ask the user to repeat it.
2. Do not treat "rise to power" as equivalent to villainy, domination, revenge or moral corruption.
3. Do not assume the character's origin, power source, motive or personality.
4. Establish the selected continuity merge policy or clearly identify what remains unresolved.
5. Build a useful world-entry frame without dumping hidden lore.
6. Distinguish public setting knowledge, restricted knowledge, disputed claims and unrevealed facts.
7. Present a diverse starting-position spectrum based on structural dimensions, not only familiar origin archetypes.
8. Include possibilities outside the obvious Cadmus/Gotham/LexCorp patterns where defensible.
9. Make clear that examples are non-exhaustive.
10. Ask only for the next consequential decision after contributing actual setting-aware design work.
11. Use the mandatory SHIPSIM interface with Unicode and a contextual emoji.
12. Do not expose secrets or hidden faction plans as known facts.

### Fatal failures

- Treating all Composite DC continuities as one settled canon without a merge policy.
- Revealing a hidden identity, conspiracy, classified facility or unrevealed power route.
- Assigning a specific origin or power without user approval.
- Reducing the setting to a handful of famous characters and organizations.

## Test N — Mystery-preserving first contact

### Input fixture

The character enters a district where:
- one building has a sealed lower entrance;
- deliveries occur at irregular intervals;
- a nearby business owner avoids discussing the building;
- no direct evidence establishes a connection between these observations.

### Pass criteria

1. Describe observable details precisely.
2. Do not claim the building is a lab, hideout, cult site or criminal facility without evidence.
3. Do not make every clue part of one conspiracy.
4. Preserve several plausible explanations internally.
5. Allow the player to inspect, ask, research, follow, ignore or return later.
6. Keep NPC knowledge separate and give each NPC a plausible information source.
7. Do not disclose the hidden explanation in a suggestion panel.
8. Do not use artificial vagueness: report what can actually be seen or heard.

## Test O — Suggestion diversity and quality

### Input fixture

The character has no urgent task, is in a populated urban district, has modest resources, and has not chosen a long-term goal.

### Pass criteria

When suggestions are useful, provide a varied set drawn from distinct domains, for example:
- local observation or exploration;
- social contact or relationship;
- education, work or training;
- practical resource acquisition;
- institutional access;
- information gathering;
- an unusual but defensible opportunity;
- a long-horizon possibility.

The exact categories depend on the actual world state. They are not mandatory slots.

Each suggestion must identify its basis, potential value, meaningful trade-off and certainty. Do not repeat one idea in different wording. Do not turn every suggestion into a quest. Do not imply the list is exhaustive. Do not expose secrets the character has not discovered.

A rejected suggestion must not reappear unless new evidence materially changes its value.

## Test P — Mandatory interface rendering

### Input fixture

The user performs a routine action that changes one item in inventory and advances time by several minutes.

### Pass criteria

1. The response contains a recognizable SHIPSIM header or compact identity.
2. It uses at least three meaningful Unicode interface glyphs.
3. It uses at least one contextual emoji in the interface/status layer.
4. It renders the action result in clear prose.
5. It reports the inventory/time delta without dumping unchanged state.
6. It returns control at a sensible point.
7. The UI is legible in plain text and does not rely on HTML.

### Failure

Any simulation response with no visible interface, no meaningful Unicode structure, or no contextual emoji fails this test.

## Test Q — UI without narrative suffocation

### Input fixture

A quiet dialogue scene with no inventory, objective or condition changes.

### Pass criteria

1. Interface remains recognizable.
2. It does not print irrelevant panels for unchanged systems.
3. Emoji and glyphs identify interface functions rather than decorate every sentence.
4. Dialogue and prose remain natural and dominant.
5. No fabricated status delta is produced merely to fill the template.

## Test R — Suggestion visibility versus hidden knowledge

### Input fixture

The simulation internally tracks a concealed organization that the player character has not encountered. The character has only observed an unusual delivery pattern.

### Pass criteria

Suggestions may point toward comparing schedules, asking local businesses, observing the delivery route or checking public records if plausible. They must not name the concealed organization, reveal its purpose or imply that the character already knows it exists.

## Test S — Character creation without forced closure

### Input fixture

The user provides a concept, two personality traits, an uncertain origin and no fixed appearance.

### Pass criteria

1. Extract and preserve supplied information.
2. Keep origin and appearance unresolved.
3. Offer useful provisional development without locking it.
4. Identify the next meaningful stage.
5. Do not force a complete character sheet or a long questionnaire.
6. Accept freeform, partial and contradictory notes as material for refinement.

## Evaluation rubric

Score each test from 0 to 4:

- **0 — Failure:** violates a fatal or major criterion.
- **1 — Weak:** recognizes the requirement but misses most operational details.
- **2 — Partial:** succeeds in some areas but has material omissions or regressions.
- **3 — Pass:** satisfies all critical criteria with minor quality issues.
- **4 — Strong pass:** satisfies criteria and demonstrates depth, specificity and coherent execution.

A candidate fails overall if any fatal failure occurs or any test scores below 3. Record the exact model, prompt version, test input, full output, score, failure class and corrective change.
